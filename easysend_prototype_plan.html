EasySend — Website Prototype Plan

Send and receive items through commercial flight passengers. EasySend is a web platform connecting senders with travelers on the same route — cheaper and faster than traditional couriers.

This document outlines the website pages, features, and 8-week development plan for the EasySend prototype.

Problem & Solution

Why EasySend exists.

🚧

The Problem

International shipping is expensive and slow. Small senders in regions like Azerbaijan pay high courier fees and wait days or weeks, with no visibility along the way.

✈️

Our Solution

EasySend connects senders with passengers flying to the same destination. Travelers carry the item using spare luggage allowance and earn money. Everyone wins.

How It Works

4 simple steps on the website.

1

Post a Package

Sender fills a web form with destination, weight, and item details.

2

Traveler Accepts

A verified traveler on the same route accepts the request online.

3

Meet & Fly

They meet near the airport. Traveler takes the package on the flight.

4

Confirm Delivery

Recipient enters OTP on the website. Traveler gets paid automatically.

🧳

  • Browses open requests
  • Accepts a delivery
  • Chats with the sender
  • Gets paid after delivery
📬

Recipient

  • Receives email with OTP
  • Opens tracking link

8-Week Development Plan

What to build each week for the website prototype.

Week 1
Plan & Set Up
  • Decide which pages to build first (Home, Sign Up, Post Package)
  • Set up the project: create GitHub repo, folder structure
  • Install tools: Node.js, React, database
  • Sketch all 10 pages on paper — agree on the layout as a team
Output: Project set up + paper sketches of all pages
Week 2
Home Page + Sign Up
  • Build the Home page: headline, how it works section, Send / Carry buttons
  • Build Sign Up and Login pages with a form
  • Add role selection: "I want to send" or "I want to carry"
  • Make it work — user can register and log in
Output: Live Home page + working Sign Up / Login
Week 3
Post Package + Browse Requests
  • Build the "Post a Package" form page (destination, weight, description, budget)
  • Save form data to the database when submitted
  • Build the "Browse Requests" page — show posted packages as cards
  • Add basic filtering: by destination city
Output: Sender can post, traveler can browse
Week 4
Accept Delivery + My Deliveries
  • Add "Accept" button on the request detail page
  • When accepted, update status from "Open" to "Accepted" in database
  • Build "My Deliveries" page — list of deliveries for sender and traveler
  • Show status label on each delivery: Open / Accepted / In Transit / Delivered
Output: Traveler can accept, both sides see their deliveries
Week 5
Chat + Tracking Page
  • Build a simple message thread between sender and traveler
  • Messages saved to database, refresh when page reloads
  • Build the Tracking page — show delivery steps as a visual progress bar
  • Steps: Posted → Accepted → In Transit → Delivered
Output: Working chat + delivery tracking page
Week 6
OTP Confirmation + Profile Page
  • When traveler marks "Delivered", send a 6-digit OTP to the recipient's email
  • Build the OTP entry page — recipient types code to confirm delivery
  • On confirmation, mark delivery as complete and release payment
  • Build the Profile page — show name, photo, rating, completed deliveries
Output: Full delivery flow works end to end
Week 7
Fix, Polish & Test
  • Go through the full flow yourself — find any broken steps
  • Fix bugs, improve button labels, fix any confusing pages
  • Make the website look clean on both desktop and mobile
  • Ask 3 people outside the team to try the website and note feedback
Output: Polished, working website prototype
Week 8
Deploy + Present
  • Deploy the website online so it's accessible by URL (use Vercel or Railway — both free)
  • Record a 2-minute screen demo walking through the full flow
  • Prepare presentation slides: Problem, Solution, Demo, Business Model
  • Be ready to show the live website during the presentation
Output: Live website URL + demo video + slides

Risks to Know About

Common issues and how to avoid them.

Running out of time on complex features

If chat or payments take too long, skip them in Week 5–6 and fake them with static data. Show a "Chat coming soon" placeholder. Delivery of the full flow matters more than perfect features.

Backend bugs blocking the frontend

Build with dummy/hardcoded data first. Connect the real database only after the page looks correct. Don't wait for the backend to design the frontend.

Website not working on mobile

Use CSS Flexbox or a simple framework like Bootstrap from the start. Check on phone every week, not only at the end.

Deployment issues in Week 8

Don't wait until Week 8 to try deploying. Try Vercel in Week 5 or 6 so there are no surprises during the presentation.
